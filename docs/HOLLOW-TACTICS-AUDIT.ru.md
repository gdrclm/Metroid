# Аудит Hollow Tactics V4 и покрытие полного ТЗ

Цель: повторно использовать работающие части пользовательского прототипа, сохранив полный объём исходного GDD. Это анализ и проект переноса, не внедрение механик в основную игру.

Источники: [полный GDD](reference/GUIDE-FEATURES.en.md), [оригинальный HTML](reference/hollow-tactics-v4.html), [архитектура ИИ](HERO-AI-ARCHITECTURE.ru.md), [результаты браузерных сценариев](reference/hollow-tactics-v4-audit.json).

Оригинал HTML сохранён без изменений: 41 217 байт, SHA-256 `c10ecdb3f7443d52ec095533c7d3f1a9d0531fcea387832572e99909c97307d2`.

## 1. Как проверено

Прочитан весь HTML, включая встроенный JavaScript. Внешние скрипты, сетевые зависимости и скрытые модули в нём отсутствуют. Проведены девять сценариев в Chromium/Playwright. Для воспроизводимости harness вручную продвигал callbacks `requestAnimationFrame`, а генератор случайности возвращал 0,75. Сценарии использовали функции прототипа; его исходник не исправлялся.

Это диагностические прогоны возможностей и ограничений, а не утверждение, что прототип прошёл требования полной игры. Базовые состояния героя выставлялись на допустимую опору с зазором 0,1 пикселя, соответствующим его собственной обработке посадки.

## 2. Подтверждённые компоненты

| Компонент | Функции прототипа | Результат и использование |
|---|---|---|
| Тактическая пауза | `toggleTacticalPause`, `update` | Герой и враги действительно останавливаются; переносим сценарий переключения в общий менеджер режимов |
| Живая очередь | обработчик canvas, `addImmediateCommand`, `advanceCommand` | Приказ можно добавить и на паузе, и при движении; сохраняем такой способ взаимодействия |
| Редактирование очереди | `removeQueueItem`, `removeCurrentCommand`, `clearCommands`, `updateQueueUI` | Удаление ожидающей команды работает; отмену активной надо сделать атомарной |
| Дополнительный прыжок | `executeCommandLogic`, посадка в `update` | Первый импульс, дополнительный воздушный импульс и восстановление заряда при посадке подтверждены |
| Направление рывка | `hero.facingDir`, ветка `hero.isDashing` | В проверке рывок стартовал влево с `vx = -7.5`, без самопроизвольного разворота |
| Слабый герой без приказа | `executePassiveAI` | Есть отдельный режим блуждания: `vx = 0.8`; можно адаптировать как предложение фоновой политики |
| Враги с физикой | `updateEnemiesPhysics` | Есть состояния `patrol/chase`, радиус обнаружения, гравитация, реакция на край/стену и контактный урон |
| Прогноз движения | `drawPredictiveTrajectory` | Копируются герой и очередь, строится полилиния с учётом прыжка/рывка; это заготовка Oracle |
| Разрушаемая геометрия | ветка `attack` | Удар действительно меняет плитку типа 2 на пустоту; это дополнительная возможность прототипа |

## 3. Ограничения, воспроизведённые в браузере

| Наблюдение | Фактический результат | Требование к переносу |
|---|---|---|
| Лимит очереди отсутствует | Приняты пять приказов; после удаления остались четыре и четыре бейджа | Лимит три, включая активную команду; единый валидатор для клика и кнопок |
| Частицы продолжают жить на паузе | За пять кадров герой/враги неподвижны, срок частицы уменьшился | Мир и его частицы используют остановленные часы; UI может анимироваться отдельно |
| Отмена рывка не отменяет его физическую фазу | После удаления активного приказа `isDashing` остаётся `true`; активен следующий `move`, но после окончания рывка он исчезает | Привязать фазу к ID команды; завершение отменённого действия не продвигает другую команду |
| Атака поражает врага позади героя | Герой смотрел вправо, враг слева был удалён | Использовать направленный `attackBox`, LOS, здоровье и реальные окна атаки основной игры |
| Прогноз пропускает последствия атаки | После `attack → move` прогноз заканчивается на X=227,9, исполнение достигает X=255,4; плитка меняется с 2 на 0 | Общее исполнение атаки и изменения геометрии в копии симуляции |
| Заблокированный `move` не завершается | После 500 кадров приказ всё ещё активен, X=215,9 | Тайм-аут, код причины и остановка зависимой части плана |

Дополнительно установлено чтением кода:

- `gameLoop` вызывает `update` один раз на кадр; скорости, гравитация и таймеры не используют `dt`. Числа нельзя переносить как настройки основного контроллера 120 Гц.
- Предсказание отдельно повторяет физику, не моделирует врагов, урон и разрушение; линия всегда синяя. Нет классификации зелёный/жёлтый/красный.
- После окончания очереди прогноз прекращает движение, тогда как живой герой начинает случайное блуждание. Горизонт прогноза и политика пустой очереди должны иметь один контракт.
- Команда прыжка передаёт управление на апексе. Это позволяет следующему прыжку сработать в воздухе; обязательное ожидание посадки в новом исполнителе сломало бы эту цепочку.
- Недоступный прыжок молча пропускается. Нужен результат `capability_missing/no_charge`, доступный игроку и Oracle.
- Клик хранит только `clientX - rect.left`; нет преобразования камеры/масштаба, выбора цели по Y и прицеливания по конечности.
- Нет сохранений и версий команд/комнаты. Нельзя переносить живые ссылки на врагов через смерть или загрузку.

## 4. Решения по повторному использованию

1. Перенести сценарии UI и переходы команд, сохранив живое добавление, редактирование, дополнительный прыжок и направление рывка.
2. Направить их через один валидатор, FSM и `HeroInput` в существующую физику Metroid. Не подключать ещё один `requestAnimationFrame` с отдельным изменением мира.
3. Использовать копирование состояния/очереди как основу Oracle, но заменить дублированную физику общей симуляцией. Прогноз должен воспроизводить эффекты команд.
4. Превратить слабое блуждание и реакции врагов в предложения поведения, а не в запись `vx/vy` поверх команды Проводника.
5. Подключить разрушение к событиям изменения геометрии и версии мира. Оно остаётся дополнительной механикой прототипа; полного набора вмешательств из GDD это не заменяет.
6. Выдачу воздушного прыжка согласовать с прогрессией I акта: базовая возможность из HTML не должна обесценить обязательные ранние шлюзы рывка и зацепа.

## 6. Что считается завершением следующего этапа

Для I акта должны работать и быть проверены G01–G15 и G18–G21 в рамках действующих правил акта. Ни Вокзал, ни Кварталы не становятся II или III актом. Оставшиеся строки сохраняются в плане полной игры; их программные сценарии проверяются отдельно от маршрута I акта и включаются сюжетными воротами.

Документ не обозначает механику «готовой» только потому, что есть её кнопка, поле состояния или тип команды. Нужны исполнение, влияние на мир, корректная отмена/пауза и проверка результата.
